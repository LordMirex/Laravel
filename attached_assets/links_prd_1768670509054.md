1. Executive summary

Build a designer-first, template-driven, modular Laravel application that authors, creators and influencers can install on shared hosting. It is distributed as a single package that boots into a web-based setup wizard on first run. The product focuses on high-quality landing pages (designer templates like premium celebrity/brand stores), a flexible block-based content engine, native newsletter functions, and WhatsApp commerce.

High-level promise: A non-technical creator can pick a premium template, edit their content via a visual admin, toggle features (store, events, newsletter), and go live on shared hosting with no developer help.

⸻

2. Goals, constraints & success metrics

Primary goals
	•	Deliver premium, production-quality templates that feel custom.
	•	Keep content portable: switching themes preserves creators’ data.
	•	Build robust first-run installer that works for typical cPanel setups.
	•	Support native mailing and WhatsApp commerce without third-party dependencies.

Constraints
	•	Target environment: shared hosting (cPanel/File Manager), PHP 8.2+, MySQL.
	•	Minimal server permissions: cannot assume SSH, background workers, or advanced PHP functions on all hosts.
	•	Single install per package; no SaaS multi-tenancy in v1.

Success metrics
	•	Fresh install success rate ≥ 90% across tested cPanel hosts.
	•	Admin ability to edit hero, enable store, and publish in < 5 clicks.
	•	Landing page TTFB < 800ms on cached pages in typical shared hosting (with CDN).
	•	Newsletter delivery success > 80% when SMTP configured.
	•	1st-day buyer satisfaction (survey) > 85%.

6. Product concept: template → theme → content (detailed)
	•	Template — structural layout: component placement, hero style, page flow.
	•	Theme variant — visual skin: tokens for colors, typography, animation.
	•	Content — canonical data (bio, socials, products, media) stored separately (DB or JSON).

Switch behavior
	•	When a theme or variant is applied:
	•	Presentation layer changes (CSS variables, component classes, partials).
	•	Canonical content is re-rendered in the new design — no data migration needed.

Why this approach
	•	Designers produce premium layouts that are preserved.
	•	Creators can change their look without losing content.
	•	Developers maintain a single canonical data model.

9. Theme engine and token architecture (detailed)

Tokens: JSON objects that map to CSS variables:
	•	Colors: primary, secondary, accent, text, bg
	•	Typography: font stacks for heading & body, sizes scale
	•	Spacing: container widths, gutters
	•	Radii and shadows
	•	Interaction tokens: hover scale, durations

Variant file structure
	•	theme_name/variant_id/
	•	tokens.json
	•	components/ (optional blade partial overrides)
	•	preview.png thumbnails

Runtime
	•	When admin applies a variant:
	•	Save site_settings.theme = variant_reference
	•	On render: inject CSS variables from tokens into <head> or generate inline critical CSS
	•	Blade components read tokens for layout decision where needed.

Designer deliverables per variant:
	•	Figma file (all breakpoints)
	•	token JSON
	•	asset pack (hero images, sample product images)
	•	component mapping (hero variant A → hero.variantA.blade.php)

11. Installer & packaging — first-run logic, error handling, fallbacks

First-run detection
	•	Check order:
	1.	storage/installed.lock exists → installed
	2.	APP_ENV or .env presence and INSTALLED=true → installed
	3.	No installed → installer mode active

Installer steps
	1.	Server & DB test
	•	Input DB host, port, name, user, password.
	•	Test connection (AJAX).
	•	If blocked: provide SQL dump + manual import instructions.
	2.	Migrations & seed
	•	Attempt Artisan::call('migrate --force').
	•	Seed templates and settings.
	•	Show step logs. If fail: show exact SQL error and safe manual steps.
	3.	Admin create
	•	Collect name, email, password, timezone.
	•	Create admin user.
	•	Optional: seed demo content toggle.
	4.	Site identity & theme
	•	Site title, WhatsApp phone, currency, select category & theme.
	•	Save settings & create installed lock.

Edge cases & fallback
	•	If proc_open/exec disabled:
	•	Provide database/schema.sql in package and show step-by-step phpMyAdmin import instructions.
	•	After manual import, ask admin to click “I imported” and proceed.

Installer UX
	•	Progress bar, clear error texts, support link with prefilled diagnostic info (PHP version, extensions, DB error).

Security
	•	Installer route removed/disabled after success.

12. Newsletter & email delivery architecture (shared-host robust)

Principles
	•	Build for two modes: queued workers (optimal) and synchronous chunked sending (fallback).
	•	Always recommend SMTP provider in README.

Implementation guidance
	•	Store subscribers table with tags and sources.
	•	Mail sending modes:
	•	Queued: push SendNewsletterJob to queue (batch), worker processes.
	•	Synchronous fallback: chunk subscribers (size configurable, default 50) and send with sleep(1) between chunks; show progress and warn about timeouts.

Admin features
	•	Compose editor (rich text), subject, preheader.
	•	Test send to admin address.
	•	Segment selection (all, tag, imported list).
	•	Scheduling (store campaign with scheduled timestamp; trigger via cron or admin manual send).

Unsubscribe
	•	Add unsubscribe token link; toggles opt_in=false.

Deliverability docs
	•	README: Steps for Mailgun/Sendinblue SMTP setup with examples; DKIM/SPF basics.

16. Performance, hosting, and cPanel-focused operational notes

Performance targets
	•	Cached landing page render < 800ms TTFB (depends on hosting).
	•	Perceived load: LCP < 2.5s on mobile with CDN & optimized images.

Shared-host constraints
	•	Avoid relying on long-running background processes.
	•	Use chunked processing for heavy tasks.
	•	Avoid expensive image transforms on the fly; generate variants at upload.

cPanel-specific tips
	•	Installer must handle public_html path variations (some hosts use /public_html, some /www).
	•	Provide a helper route for creating symbolic link to storage if php artisan storage:link not usable.
	•	Provide alternative instructions for setting file permissions if chmod not available from PHP.

Recommended minimum hosting
	•	PHP 8.2, MySQL 5.7+, 256MB PHP memory, Imagick (optional but recommended), SMTP access.

19. Troubleshooting guide for common cPanel problems

DB connection errors
	•	Check DB host: often localhost on cPanel; some hosts use separate DB servers.
	•	Check port (3306) and DB user permissions (GRANT privileges).
	•	Provide sample phpMyAdmin import instructions.

Artisan migrate fails
	•	Provide database/schema.sql + instructions to import and then run seeder steps that can be executed via web endpoint (protected) if allowed.

File permission issues
	•	Suggest 755 for storage and bootstrap/cache and provide cPanel File Manager steps to set permissions.

Mail sending fails
	•	Suggest setting up SMTP credentials in Settings; test with test mailbox and show SMTP debug log.
